## 4. 已证实的关键问题

### F01｜官方语料工作区根本没有向量索引【P0】

主库工作区 `031dcae328aa4df2a24167d69d8f14c6`：40 个文档版本，1987 页，其中包含 39 份原始测试文档和 1 页裁剪辅助文档；25,145 个活动解析块，**0 条活动块向量**，`dense_pages=0`。全库其他工作区存在部分 Gemini 向量，不能据此认定官方语料已具备混合检索。

只读运行该工作区 Transformer v7 检索：

| 输入 | 当前返回 |
|---|---|
| 第六作者是谁？ | keyword，0 个块 |
| 训练用了多少张显卡？ | keyword，0 个块 |
| number NVIDIA P100 GPUs | 找到含 8 张 P100 的原文 |
| Adam beta1 beta2 | 找到优化器段落，但首个候选是 Adam 参考文献 |

这是一组定向诊断，不是总体准确率。说明当前中文自然提问和英文论文之间存在直接断点。`retrieval.py:21-78` 硬编码 Gemini 索引路径，尚无本地模型适配。

修复：统一 EmbeddingProvider；完成全部符合索引策略的活动块覆盖；显式区分不可检索块、已索引和失败。后台全量生成完成后原子切换索引，不覆盖旧证据。中文查询同时做真正跨语言向量召回与受控英文检索表达；稀疏中文索引和查询使用一致分词。仅在 query 端拆二字词，配合原文 `unicode61` 索引，不能实现中文分词匹配，已用隔离 SQLite 探针证实。

### F02｜“引用存在”并不等于“结论有依据”【P0】

`jobs.py:76-102` 验证 block ID、引文子串、页码和坐标，状态诚实写为 `located_semantics_pending`。但没有检查主张的语义支持，也没有检查自由正文 `answer` 与结构化 `claims` 是否一致。

新增三个构造反例均被当前函数接受：

1. 给定引文写 8 GPUs，主张写 80 GPUs。
2. claims 正确写 8 GPUs，但 answer 写 80 GPUs 和无出处费用。
3. quote 为纯空白字符串，也通过子串检查。

这是对校验器的反例，不是声称历史真实模型曾输出这些错误。

修复：规范化后拒绝空引文；原文偏移与跨块 span 校验；事实拆成原子 claim；数字、单位、实体、日期、实验条件做规则检查；独立审查上下文输出 supported/contradicted/insufficient；无法复核不能标绿。正文由经审查的 claim 渲染，或用 answer_segments→claim_ids 逐段绑定。Reranker 只判相关性，不能代替语义证据审查。机器复核也不是数学证明，应保留人工复核入口。

### F03｜两个项目的配额没有真正调度【P0】

`models.py:92` 使用 `next(_choose(...), None)`，后续只对第一个项目 reserve。即便第二项目有额度，第一项目日额度耗尽仍直接失败。隔离探针确认只尝试第一个项目。

同时，历史四次 Hydrogen smoke 预算已耗尽；默认 `RT_SMOKE_MODE=true`，新增密钥不等于解除该持久化限制。线上模型配置存在，也不等于还能回答新问题。

修复：配置独立的开发、评测、评审预算；保留真实账本；按实际 project_id 去重，只在请求尚未发出且本地预留失败时尝试其他有授权的项目。已发出但超时的请求不得盲目重发。根据用户确认的实际项目额度设置预算，而不是宣称两个 key 自动翻倍。付费兜底仍需明确授权。请求消耗和单工作流请求上限均可见。

### F04｜外部检索在原环境受阻，Future Work 还未形成自动闭环【P0/P1】

包内最新限制记录：arXiv/Crossref 在原机解析到代理 fake-IP 地址 198.18.2.x，被 SSRF 正确阻止。不能把该事实替换为“API 返回 200 即检索成功”。本轮未连接你的真实主机复测网络。

`jobs.audit:230-276` 虽然会搜索候选，但没有将候选自动获取合法全文、解析并纳入此次审查；实质判断依赖工作区已有其他论文。它按年份排除同年文献；原文年份未知时又可能将其他文献放入 later 集。需要更明确的时间证据，而不是只比 year。

修复顺序：先修原主机 DNS/可信代理路径，保留地址校验与 DNS pinning；再做 query plan→多源发现→DOI/arXiv 去重→可访问全文→解析→条件比较→结论及检索边界。记录发表/首次提交/具体版本时间，区分同年后续工作、修订版和时间未知。OpenAlex 可补充元数据和引用链，但要按当前官方访问规则配置 key 与预算，不假设无限免费。[S8][S9]

### F05｜当前 Agent 是可靠固定流程，但自主规划不足【P1】

`jobs.py:144-192` 的 plan 是固定 retrieve/synthesize/validate/save。额外工具由问题中的少量正则触发；工具结果摘要存入 ret，但主生成 prompt 只传版本、文本证据等，没有系统地向模型反馈额外工具完整结果。现有注册表、参数校验、预算与日志是真实资产，应复用。

升级为有界的三角色协作：Planner 产生可执行计划；Evidence Worker 执行检索、版本比较、图谱、下载；Critic 对证据缺口和矛盾提出有限次补检索。角色需有独立上下文、输入输出和真实执行分支，不能只在前端显示三个名字。简单事实问题走短路径，复杂任务才调用规划与审查；限制循环、调用数、token 和副作用。LangGraph 的持久化/中断能力可参考，但不要在已稳定的 SQLite 任务系统旁再建一套互相冲突的状态真相。[S6]

### F06｜明确的赛题覆盖缺口【P0】

- `app.py:155-156` 每请求最多 10 文件，`documents.py:104-110` 每工作区同时待解析任务上限 10；因此只把前端选择数改成 20 仍不够。应增加上传批次实体、逐文件状态和待入队分批调度，允许一次选择 20 篇、内部有界处理。官方要求不等于必须一个原子 HTTP 请求。
- `jobs.py:194-228` 翻译硬编码为简体中文；API 没有目标语言，缓存主键没有方向。补 source_language/target_language、术语表版本和模型信息，支持中→英；避免英→中缓存误复用。
- 写作现在主要复用普通问答，未形成论文大纲的结构化章节状态。架构图编辑器已有，但“从论文逻辑自动生成”还需串起模型计划、受控代码输出和安全预览。

### F07｜本地模型部署不是改一个模型名【P0/P1】

当前生成与 embedding 都走 Google API。解析适配通过 Unix socket 连接本机 broker；不能直接在 ECS 配上远端 3090 的路径就工作。worker 单进程循环执行，长解析可能占住其他 AI 任务。

新增独立推理服务与认证的私网传输，保留本机 UDS 选项；ECS 只做轻量 API/数据库/网页与调度。GPU 服务不要暴露未认证公网端口。解析、索引、问答分执行池/优先级与资源槽，不抢占别人的进程。当前 parser GPU 默认预算 2048MiB 是为其保守测试设计，不适合直接承载 8B 模型；应分服务配置预算，不能粗暴关闭 guard。

### F08｜前端有审美基础，但工作场景被管理控件挤占【P1】

包内截图显示：蓝白配色、组件一致性、证据定位已可用。当前最明显的问题不是“不够炫”，而是阅读器四列占宽：全局导航、解析控制栏、PDF、问答同时铺开；默认解析引擎/CPU/快照等管理项比目录更醒目；任务 JSON 与步骤占据回答区；目录出现版权文字等误识别标题；图谱把大量节点和标签放在近圆形布局，交叉边很密。

## 5. 模型选择的研究依据与落地约束

### 5.1 为什么这次不直接选 Qwen3-Embedding-8B

Qwen3-Embedding-8B 是可靠对照，支持长文本和可变维度，官方公开权重；但它不是当前唯一高质量候选。[S3]

NVIDIA 于 2026 年 10 月发布 Nemotron 3.5 Embed/Rerank：能对文本、PDF 页面图像及图文组合检索、重排。科研论文中的表格、图和扫描页正好需要这类能力。官方模型卡在其 ViDoRe V3 协议下报告，8B 图文检索 61.47，对照 Qwen3-VL-Embedding-8B 为 57.03；相同候选集下，3.5 Rerank 的图文结果 67.56，对照 Qwen3-VL-Reranker-8B 为 66.03。这里比较的是 **Qwen3-VL** 而不是纯文本 Qwen3；是供应方评测，不能移植成 ResearchTrace 的提升幅度，也不能混用 V3 和 V3.1 数字。[S1][S2]

Microsoft Harrier-27B 在其 MTEB v2 综合任务上报告 74.3，但综合分不等于科研检索分；27B BF16 仅权重约 54GB，跨卡部署对共享显卡的稳定性提出更高要求。因此不把它列为此次默认在线模型，只作为资源充分且有时间时的离线挑战者。[S4]

Nemotron 3.5 的文本语言组件从对应 Nemotron 3 冻结而来，官方预期文本向量保持不变。选择 3.5 的主要增量是多模态，不应宣称仅因版本号更新就纯文本大幅提升。[S5]

### 5.2 部署必须写入任务书的细节

先在一张有足够空闲显存的 3090 做批量 1、短序列 smoke，记录 CUDA/驱动、峰值显存、冷启动与延迟。8B BF16 仅权重约 16GB，不等于总运行占用；两套 8B 不应默认共住同一 24GB 卡。最佳是分别获得两个稳定资源槽；若不能保证，明确排队/降级，不宣称评审服务可全天稳定。

优先独立 Transformers 环境实现简单服务，再按吞吐需要考虑 vLLM。官方当前示例对 Transformers 与 vLLM 的依赖版本有冲突范围，不能混装到现有 MinerU/Paddle 环境。不要照抄 32K 满上下文与大 batch 默认值；不要使用针对 Blackwell 优化的 NVFP4 作为 3090 默认部署。[S1][S2]

必须锁定模型 revision、tokenizer、chat template、pooling、normalization、维度、精度、chunker 版本。Nemotron 使用官方 query:/passage: 模板、mean pooling 与 L2 normalization；Qwen 的配置单独实现。不同模型/配置向量不混用，即使维度相同。云端兜底只有在相应独立索引已建立时才有效。

## 6. 推荐的最终检索与证据架构

`原始 PDF → 不可变解析块 → 结构化检索 chunk → 文本/视觉索引 → 混合召回 → 重排 → 证据包 → 生成 → 语义与数值审查 → 可核验产物`

1. **解析块不等于检索块。** 不改旧 block ID；另建 chunk 对应多个 block/span。首版实验从 400–800 tokens 子块、父章节上下文入手，表格保留表头、单位、脚注，不能截断原块前 5000 字符后假装整块已索引。
2. **上下文增强。** 检索文本带论文标题、章节路径、表/图编号。先用可验证元数据，不必给每个块额外调用大模型生成背景；若采用模型生成摘要，独立标注，不作为原文引用。上下文增强检索与重排有成熟方法可参考，但效果需本集验证。[S10]
3. **候选多路。** BM25 保留精确术语数字；本地向量负责语义及跨语言；问题涉及图像才加入视觉候选。RRF 后对 Top 30–50 重排为 8–12 个证据包，跨论文比较确保每篇有机会召回。数字计算在结构化单元格和单位校验后程序执行。
4. **向量索引。** 当前逐条 SQLite blob+Python dot+逐块查询应改成批量矩阵/FAISS。约 2.5 万块 ×4096×4 字节为约 412MB 原始向量，尚未计额外结构；放 GPU 服务器侧的 CPU 内存更合适。先使用精确内积索引，只有规模证明必要时再用 ANN，避免无端损失召回。[S11]
5. **证据坐标。** 文本匹配可定位句段；视觉检索命中页面不代表已获得单元格坐标。缺少精细框时只给页/区域级定位，禁止伪造高亮。
6. **解析质量门控。** 保留 native 快速预览，复杂双栏/表格/公式进入现有 MinerU，高难页按需 PaddleOCR-VL；检查标题、作者顺序、单位和公式。GROBID 可专项增强作者/机构/参考文献字段，不必替换全文引擎，也不要部署到 2GB ECS。[S12]

## 7. 最值得做成评审记忆点的三条演示

### A. 证据审计型问答

上传没预置过的论文，评委用中文问训练配置；系统给结论、具体版本、原文定位。再提一个错误前提问题，例如“为什么用了 80 张 GPU”，系统指出原文是 8 张并展示支持片段。另问文中不存在的费用，系统明确缺证据。

亮点不是“回答多流畅”，而是它能区分找到出处、出处支持主张、以及主张超出原文。不能预录假装实时；应记录运行 ID、耗时和缓存状态。

### B. 版本变化影响研究笔记

先就旧版生成有出处的笔记，再上传改名的新版本。展示章节对齐差异，以及已有主张“仍获支持 / 来源变化需复核 / 尚无法判断”。不自动改写旧结论、引用或历史快照。差异过小也如实展示，不能为了演示编造变化。

### C. Future Work 证据时间线

从原文 Future Work 选一个问题，自动检索后续文献，拉取许可允许的全文，展示时间、任务、假设、数据集和覆盖条件矩阵。输出“已有直接相关证据 / 部分覆盖 / 当前范围证据不足”，点击每个状态能看到比较的原文。把新增论文接入后重算，而不是固定几张卡片。

这三条能同时体现智能解析、高级 RAG、Agent 工具、创新、交互与实用性。全部必须先可靠完成，再录制视频。

## 9. 评价标准：用实测决定是否换默认模型

建立 80 条人工可核对的检索题：24 事实/数字/作者，16 中英改写，12 多文比较，12 表格/公式/图像，8 版本敏感，8 无答案或错误前提。按论文 work 分离调参与保留测试集，避免同一篇不同版本分别进入两组。39 个官方样例用于兼容性，补充未见论文用于泛化；不要把官方答案或完整 gold 写入被测系统提示词。

对比固定切分与条件下的：FTS 基线、已有 Gemini 向量配置、Qwen3-8B、Nemotron3.5-8B、Nemotron+Reranker、按需视觉。前四组先控制切分一致；结构切分变化另外做消融。记录 Recall@20/nDCG@10、证据支持率、数值/条件正确率、错误前提处理、原文定位、P50/P95、显存、请求数与降级率。纯检索题不消耗 Hydrogen；生成质量用独立有预算的子集，不能让评测耗尽演示额度。

建议内部目标（不是官方及格线，也不是已经达成）：有答案题 gold evidence Recall@20≥95%；人工逐主张证据支持率≥95%；有出处事实正确率≥90%；拒答/纠错≥90%；引用版本/页码/区域准确率≥98%；关键端到端路径全部成功；公共服务达到明确的评审资源保障。小样本结果须报告分子分母和不确定性。

部署准入：P0 全关；没有 BLOCKED 的核心演示路径；三条现场新输入流程跑通；权重、模型、代码、指标、视频与实际网页一致。不得把 48/64 工程验收换算成官方得分，不预测第一名概率。
